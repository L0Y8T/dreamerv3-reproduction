## 2 设置

| 项 | 值 |
|---|---|
| 环境 | DMC Proprio `walker-walk`（状态输入，非图像，不涉及渲染） |
| 预算 | **5.1e5 步 / seed**，`eval_every=1e4`（⇒ 51 个 eval 点），不早停 |
| 算法 | `model.rep_loss=dreamer`（DreamerV3 基线）vs `r2dreamer`（ICLR 2026 变体） |
| 模型 | `size12M`（deter 2048 / hidden 256 / discrete 16 / depth 16 / units 256） |
| batch | 16 × 64；`env_num=16`、`action_repeat=2`、`train_ratio=512` |
| seeds | 0 / 1 / 2（每臂 3 个，共 6 个 run） |
| 运行环境 | **WSL2 Ubuntu 26.04**，Python 3.11.18，torch **2.6.0+cu124**，**triton 3.2.0**，`model.compile=True` |
| 硬件 | RTX 4090 Laptop（16376 MiB）/ i9-13980HX 32 逻辑核 / 127.7 GB |
| 总墙钟 | **约 24 小时**（11-03 01:05 → 11-04 04:59），全程单训练进程串行 |

### 为什么迁到 WSL2

Windows 上没有 `triton` 的官方 wheel，`torch.compile` 的 inductor 后端必崩
（`BackendCompilerFailed: Cannot find a working triton installation`）。
实测吞吐差：

| 环境 | 稳态吞吐 | 满预算单 seed |
|---|---|---|
| Windows + eager（`compile=False`） | **5.01 steps/s** | 28.25 h |
| WSL2 + `compile=True` | **约 45–49 steps/s** | 约 4 h |

⇒ **约 10 倍**。这是这次唯一的"提速"手段，不是靠调超参。

## 3 三条判据的逐条计算

### 判据 1 · 曲线真的在学

窗口 `W = max(2000, 预算//5)` = **100,000 步**（跑了 24 万步那次窗口是 4,000）。

| arm | 前窗口均值 | 后窗口均值 | Δ | SE | 2·SE | Δ/SE | 判定 |
|---|---|---|---|---|---|---|---|
| dreamer | 155.08 | 681.26 | 526.18 | 98.42 | 196.84 | 5.35 | **通过** |
| r2dreamer | 211.20 | 847.88 | 636.68 | 39.76 | 79.52 | 16.01 | **通过** |

逐 seed 的 Δ：dreamer 393.18 / 718.35 / 467.00；r2dreamer 651.38 / 697.01 / 561.65。

### 判据 2 · 跨种子稳定

必须同时满足 `sd/mean < 0.25` **且** `mean > 0`。

- dreamer：0.215 → 通过（**但接近阈值**）
- r2dreamer：0.022 → 通过（极稳）

### 判据 3 · 两档可分

Welch：`SE = sqrt(sd₁²/n₁ + sd₂²/n₂)`，`|Δ| > 2·SE` 才算分开。
2.57·SE > 2 ⇒ **可分（dreamer 低）**，但**余量只有 28%**。

## 4 和 2e4 小预算档的对比（这次最重要的一条）

| 档 | dreamer | r2dreamer | \|Δ\|/SE | 判定 |
|---|---|---|---|---|
| 2e4（11-02 跑） | 102.60 ± 45.54 | 106.89 ± 8.09 | 0.16 | **未区分** |
| **5.1e5（本次）** | **683.27 ± 147.23** | **903.43 ± 19.51** | **2.57** | **可分** |

**小预算阶段看不出差异，不是「两臂相当」，而是「曲线还没长开」。**
预算加 25 倍后差距才显形。这条直接否掉了「用小预算快速比较算法」的做法 ——
在 Dreamer 这类模型基方法上，样本效率的差异是**在后半程才拉开**的。

### 一个两档独立复现的现象

**dreamer 的种子方差始终远大于 r2dreamer**：

| 档 | dreamer sd/mean | r2dreamer sd/mean | 倍数 |
|---|---|---|---|
| 2e4 | 0.444 | 0.076 | 5.9× |
| 5.1e5 | 0.215 | 0.022 | **9.8×** |

两次独立运行都出现同一模式。**基线对随机种子敏感、复现成本高**，这比"平均分差 220"更值得写进结论。

## 5 功耗与吞吐分析（为什么 GPU 功率上不去）

30 秒 × 1 次/秒采样（训练中）：

| 指标 | 均值 | p50 | p95 | 最大 | 最小 |
|---|---|---|---|---|---|
| GPU 利用率 | 41.3% | 46% | 61% | 61% | 0% |
| GPU 功率 | 87.8 W | 87.8 | 122.6 | **122.6 W** | 46.6 W |
| SM 频率 | 2231 MHz | 2340 | 2385 | 2385 | 1755 |

功耗墙：当前 **121.16 W** / 默认 115 / 最大 130。**峰值 122.6 W 已经撞墙。**

throttle 标志分布（30 次采样）：`0x0` 无限制 11 次、`0x20` **GPU 空闲 11 次**、`0x24` 空闲+功率 4 次、`0x4` 功率限制 4 次。

```
K: 结论：功率均值上不去，不是因为被墙压住，而是约 37% 的时间 GPU 在空闲（等 CPU 攒数据）。
K: 结构原因：batch 16×64=1024 帧对 4090 太小，一次 update 只有毫秒级，
   然后要等 16 个 DMC 环境（纯 CPU 物理仿真）走完下一轮。
K: 温度 66–70 °C，离温度墙很远；CPU 总量仅 20–26%（32 逻辑核）⇒ 不是热、不是核数不够。
X: 提高功率上限（121→130）只对峰值有效，均值几乎不动 —— 不要指望它提速。
X: 真想提上去只能加 batch / train_ratio / env_num，但那会改变算法，破坏与这 6 个 seed 的可比性。
```

## 6 这次做过的自助决定（可追溯）

| 决定 | 依据 | 影响 |
|---|---|---|
| 从 Windows 迁到 WSL2 + triton | E0 实测 5.01 steps/s ⇒ 命中 STOP-2 | 换来约 10× 吞吐 |
| Python 用 3.11 而非 3.12 | 仓库 `requires-python >=3.11,<3.12` | 依赖全对齐 |
| 依赖版本照抄 Windows 那套（numpy 1.26 / dm_control 1.0.28 / mujoco 3.3.0 / decorator 4.4.2） | 唯一已验证可跑的组合，避免把「提速」和「换版本」混为一谈 | 归因干净 |
| `model.compile=False` → 改为 `True`（两臂一致） | Windows 上装不了 triton，Linux 可以 | 两臂规则相同，对照成立 |
| logdir 改 `/root/r2d/logdir_live`（纯 ASCII） | Hydra override 语法不接受中文路径，首次启动 6 个 run 各 4 秒全死 | 零机时浪费 |
| 判据 1 窗口按预算比例 `max(2000, 预算//5)` | 写死 1e5 时，预算=1e5 会让前后窗口重合、Δ 恒为 0 | 口径自洽 |
| 判据 2 加 `mean > 0` 兜底 | `sd/mean` 在 0 分附近会爆炸 | 避免把"没学"误判成"稳定" |
