## 3 判定表（**跑之前**就写死，防止事后找理由）

主指标 = `episode/eval_score`（独立 eval envs，每 1e4 步评 10 局，取均值）。**不用 `episode/score`（训练回报）。**

| # | 判据 | 通过条件 | 不通过怎么写 |
|---|---|---|---|
| 1 | **曲线真的在学** | 见下方「判据 1 的精确算法」：`mean(d_i) > 2·SE(d_i)` | 写「复现失败」，先查 §6 的六个失败模式，**不调超参凑** |
| 2 | **跨种子稳定** | `sd(最终 eval_score) / |mean| < 0.25` **且** `mean > 0` | 写「种子方差过大」，先查 env 种子与 `env_num` 设置；若 `mean ≤ 0` 则记「不适用（曲线本就没学）」 |
| 3 | **两档可分**（仅当做了 E2） | dreamer vs r2dreamer 的最终 eval_score，按 Welch `\|Δ\| > 2·SE` | 写「未区分」，**不因为它"应该更快"就写成更快** |

### 判据 1 的精确算法（2026-11-02 两版修正后的定稿）

对每个 seed **先在自己那条曲线上**算差值，再跨 seed 检验：

```text
W = 窗口宽度 = max(2000, 预算 // 5)      # ← 比例窗口，不是固定的 1e5
d_i = mean(eval_score | step ∈ 最后 W 步) − mean(eval_score | step ∈ 最前 W 步)
mean_d = fmean(d_i)
SE_d   = sd(d_i, ddof=1) / sqrt(n)          # n = seed 数
通过条件：mean_d > 2 * SE_d
前置条件：预算 ≥ 2.5 × W（否则判据 1 记「不适用」）
```

**为什么窗口必须按比例**（2026-11-02 由执行者查出的设计缺陷，非改不可）：
初版把窗口写死成 1e5，而降级档的预算是「1e5」——两个窗口都等于整条曲线，`d_i ≡ 0`，
判据 1 **恒不通过**。这不是"没学会"，是口径自相矛盾。预算是 1e5 时窗口必须是 2e4 之类的比例值。

**不能**把「前窗口均值」和「后窗口均值」各算 sd 再拼 Welch ——
同一条曲线内相邻 eval 点高度自相关，那样算出来的 SE 会偏小、白白虚高显著性。
同一 run 内做前后对比属于配对设计，先取差值再跨 seed 求 SE 才是对的。

### 判据 2 为什么要有绝对兜底

`sd/mean` 在 mean≈0 时会爆炸（例如三 seed 都是 0 分，sd 也接近 0，比值可能是 0/0 或 0.5/0.001）。
那种情况不是「稳定」，是「什么都没学到」。所以必须同时要求 `mean > 0`，否则记「不适用」。

### 判据 3 的一个额外说明

同一 `seed` 下两臂的 eval 环境初始条件相同（`envs\__init__.py` 里是 `seed + id`），
理论上可以做配对比较、功效更高。但本项目统一口径是 Welch，**不许因为"配对更显著"就临时换方法**。
配对性只在报告里作为一句说明出现。

三个判据都只看 eval 曲线，与论文数字无关 —— 这是 C 路线能做到的最硬的自洽检验。

### 4.2 为什么要有 `export_r2d.py`

r2dreamer 用 `torch.utils.tensorboard.SummaryWriter` 写 event 文件，**不是 JSONL**。
本项目既有硬约束是「结果表由脚本从 JSONL 生成、禁止手打」，所以必须有一个导出环节：

- 读：`tensorboard.backend.event_processing.event_accumulator.EventAccumulator`（venv 里 tensorboard 2.20.0 已在，**无需装包**）
- 取：`episode/eval_score`、`episode/eval_length`、`episode/score`、`train/opt/updates`、fps
- 写：`results\<algo>-<tag>-s<seed>.jsonl`，每行
  `{"kind":"eval","step":N,"eval_score":x,"eval_length":n}` / `{"kind":"train",...}` / `{"kind":"summary",...}`
  并在首行放 `{"kind":"config", ...}`（整份 hydra config 的扁平化副本 + git commit + torch 版本）
- **沿用既有审计口径**：文件名 `{algo}-{tag}-s{seed}.jsonl`、末行必须是 `summary`

### 4.3 表与图

`table_r2d.py` 输出：
1. 每组 `n / 最终 eval_score mean±sd / 最好 eval_score mean±sd / 达标步数（可选）`
2. 判据 1、2、3 的逐条计算过程（Δ、SE、|Δ|/SE、判定）
3. 曲线图（横轴 step，纵轴 eval_score，mean ± sd 波段）

图里**必须**标出「eval 点稀疏（每 1e4 步一个点）」这一事实，别让人以为曲线是连续的。

## 5 统计口径（沿用项目既有约定）

```
K: 每组 ≥3 seeds；报 mean ± sd，sd 用样本标准差 ddof=1。
K: 判两组是否分开：SE = sqrt(sd1²/n1 + sd2²/n2)，|Δ| > 2·SE 才算分开，否则一律写「未区分」。
K: 3 seeds 时 2·SE ≈ 0.82·sd ⇒ 差异小于约 1 个 sd 一律写未区分。
X: 不许因为「3 seeds 分不开」就加种子硬凑结论 —— 「未区分」本身就是结论。
X: 不许用训练回报（episode/score）当结论，只认独立 eval（episode/eval_score）。
```

**可复现性验证（照 C006 的教训做）**：同 seed、同参数连跑两次 5e3 步，**逐 eval 点比对** eval_score 是否一致。
⚠️ 不要比文件哈希 —— 里面有时间戳，第一版就是被这个骗到误判「不可复现」。
默认 `deterministic_run: False`（快）；若两次结果不一致且超过 eval 噪声，再试 `deterministic_run=True` 并记录代价。

## 6 六个失败模式（都是这类 port 上真实会遇到的）

| 症状 | 原因 | 处理 |
|---|---|---|
| 曲线纹丝不动 / 一直 0 | 早期 eval 在随机策略期，10 局太少 | 看 `train/opt/updates` 有没有在涨；确认 `pretrain`、`train_ratio` 没被覆盖 |
| 显存 OOM | `env_num=16` + `batch 16×64` + size12M 在 16 GB 上也可能吃紧 | 降 `batch_size` 或 `env_num`，**但必须记成不同的 config**，不能和 E1 混成同一组 |
| 不同 seed 差异巨大 | 环境侧种子没固定 | 检查 `env.seed: ${seed}` 是否真被 hydra 覆盖到每个并行 env |
| 跑到一半没了 | **机器睡眠**（2026-10-28 就是这么把一波实验切成半截的） | 过夜跑之前关掉睡眠 —— **这是改系统配置，要先问用户** |
| 吞吐远低于预期 | DMC 物理仿真吃 CPU，32 线程被 16 个并行 env 抢 | 记 fps；必要时把 `env_num` 降到 8 并记录 |
| eval 点太稀看不出趋势 | `eval_every=1e4` ⇒ 满预算只有 51 个点 | 首轮先按默认跑；若曲线太粗，E2 阶段改 5e3 并记录 |
